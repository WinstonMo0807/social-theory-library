### 拟议保存规则

- 后台继续保留未发布修改与公开内容的隔离，管理员界面不再要求理解修订/草稿模型。每个对象编辑页只有一个主要保存动作，名称带对象，例如“保存书目修改”“保存学者资料”“保存理论资料”。
- 这个主按钮必须保存当前页该对象所有已修改字段，不能随当前展开区域改变范围。页面内的作者关联保存不能暗中修改学者生平；事件保存不能被说成整个理论流派已保存。
- 保存后留在原编辑位置，反馈为“已保存，尚未发布”或“修改已保存，读者仍看到原内容”；按钮附近显示时间。首次新建只建立本对象的持久地址，不送去其他列表。
- “发布到网站”与保存分开，预览明确哪些页面会更新。只在确有身份冲突、来源矛盾、人工锁等事项处要求明确核对；保留既有字段确认和审计语义，不以删按钮绕过检查，也不要求重复确认每一个无冲突区域。
- 合并重复保存必须覆盖后端事务、并发版本和失败恢复。现有 saveAllDirty 是逐节 PATCH，不可仅把顶部按钮改成调用它就宣称整对象原子保存完成；失败时需说明已保存与未保存范围，或复用现有工作编辑服务提供受版本保护的一次保存。
- 系统设置、提示词及文件操作保留自己的生效规则和权限，不强行套用书目发布。普通页面不出现无法解释的“保存草稿”。

### 时间线的归属、填写位置和公开去向

日常入口应为“知识与关联 → 理论流派 → 选定流派 → 发展时间线”。可沿用现有 `/admin/theories/{id}?section=timeline` 身份与 PublicPageTree 登记实现次级管理视图，不需要为了移动导航新建数据表或复制事件。当前 TheoryNodesAdmin 没有读取 section=timeline，而旧时间线编辑器没有把 node 参数传入列表；API 实际已支持按 node 筛选。这是对象上下文没有接通，不只是菜单文字问题。

该次级页应固定显示当前流派，新建事件默认关联它，筛选/翻页/保存/返回保持该身份。旧全库入口保留兼容访问并归入理论管理；没有对象时明确选择或查看全部，绝不默认选第一条理论。一个事件可以与多个流派相关，继续共用一个事件；保存前列出其他受影响页面，不复制多份内容。

事件表单按实际填写组织为“发生了什么”（标题、简短说明、类型）、“什么时候”（起止年、可选显示时期）、“与谁有关”（继承当前流派，其他流派/学者/作品可选）、“依据是什么”（来源说明，可选具体馆藏版本和原文位置）。未确定的年份保持未知，不伪造。列表的默认排序使用年份，手工排序放到需要时展开。

- `theory-system-admin.tsx:1542` 声称来源和证据仅在管理端，然而 `theory-timeline-public-view.tsx:42` 实际展示来源，公开 serializer 还返回 evidence_text 等字段。编辑器必须准确标明公开内容；管理备注如有需求不能借用会公开的证据字段。

### 智能辅助回到填写字段的目标

普通管理员无需管理 ResearchRun、Candidate 或字段决定。它们保留在内部，用于追溯、权限和恢复；日常动作是字段旁“帮我填写”“填入”“换一个建议”“查看来源”。不新增聊天工作台，也不要求另填一段指令后再复制粘贴。

1. 使用当前页明确对象和已有输入。人工确认/锁定值是约束；未确认手工输入也不得被自动覆盖，只能提示冲突。题名、作者、ISBN、版本、文献类型等身份信息的变化决定哪些建议需要重新查找。
2. 输入后先按已有依赖规则使受影响旧建议失效，自动重新筛选馆内记录/已有结果。已经由管理员启动且上下文仍相符的任务在当前字段显示进度并接回完成结果；需要新的外部付费调用时提供清楚的触发或经过授权的本次辅助开关，不在每个按键后全量重跑。
3. 不同字段按类型预填：年份填数字，简介填原文本框，作者逐人填姓名与职责，分类填关联选择器，图片展示并选择具体用途。填写作者不顺带创建或发布学者主页。
4. 采用内容直接可见于对应输入位置，可以修改，标记“尚未保存”；在保存时提交候选引用、修改后的值、对象版本与同一请求编号，成功后才计入采纳记录。不能仅执行 setState 而丢失原证据/人工决定。
5. 修改上游身份后，下游已有手工值原样保留，需要复核的地方说明具体原因；旧任务后完成也不能重新填回旧版本建议。拒绝过且上下文未变的同一建议不重复推荐。没找到、未配置、等待中、来源失败分别显示，不当作填错资料。

例如管理员先确定书名和作者，助手据此给出本作品的版本建议；再确定 ISBN/出版社，年份、封面、译者等应收窄到这个出版版本。换一个 ISBN 后，需要重查相关建议，不改管理员已经填好的其他值。

当前已有可复用基础是 `catalog/contracts/fields.py` 的字段依赖、`field_decisions.py:228` 的依赖失效、字段查找的上下文指纹、既有 ResearchOrchestrator 及 `research-suggestion-panel.tsx:256` 的当前表单上下文/任务查询。缺口是这些能力分散在不同控件，失效、重新建议、类型化填入、保存反馈没有形成一致流程；不是需要另造智能系统。

### 建议的普通管理员操作

默认只保留一条清楚的路径：**查看建议 → 填入表单 → 保存草稿 → 预览并发布**。

2. 作者、译者、主题、阅读路径等结构化内容使用小型确认表单，预填姓名、职责或具体关联；显示当前值与将增加、替换的内容。沿用已有对象选择器，不暴露 entity、authority 等内部术语，不把人物合并当普通采用。
3. 长简介、观点或多字段建议需要修改时，打开预填好的编辑框；不让管理员重新复制粘贴，也不强制进入聊天。封面和图片展示图片及实际用途，不转换为通用文本输入。
4. 显式保存时才将值、原候选、修改后采用信息及版本条件送给现有决定/草稿服务；结果出现在字段旁及保存栏，说明保存时间和未公开状态。候选采纳统计只在成功持久化后计入。发布保持单独确认，不因采用改变公开快照。
5. 查找不自动保存其他字段。需要基于未保存内容检索时，用有范围的表单上下文构造请求；若当前服务必须先保存，就明确显示“先保存再查找”，而不是偷偷执行。
6. 异步查找在当前字段显示排队、正在查找、已找到、没有合适结果、失败或未配置。复用现有任务标识和查询，完成后读取结果；刷新页面或轮询不能重新发起付费查找。失败保留手工输入并给出具体重试范围。
