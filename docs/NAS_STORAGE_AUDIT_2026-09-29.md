# NAS存储审计与清理建议

2026-09-28至09-29实际只读盘点。未删除用户既有文件、备份、模型、索引或volume，未修改生产数据。容量使用十进制GB；GiB单独注明。

## 35GB从哪里来

`/volume2/library/docker`实际占用37,717,913,600字节，即37.72GB / 35.13GiB，与用户看到的约35GB基本对应。它不只是当前应用目录。

| 目录 | 实际分配空间 | 主要内容 |
| --- | ---: | --- |
| `/volume2/library/docker/library-upload` | 17.74GB | 历次上传包、解包、离线依赖、Paddle编译工作区 |
| `/volume2/library/docker/social-theory-library` | 19.96GB | 当前源码、馆藏、模型、备份与回退资料 |
| 同级早期2.2.2源码/离线目录等 | 约15MB | 历史小体积部署材料 |

当前应用目录内部：

| 内容 | 实际分配空间 | 结论 |
| --- | ---: | --- |
| storage/backups | 15.15GB | 最大项，大量为发布前源码/运行时归档，不全是数据库备份 |
| storage/models | 2.15GB | 现用及兼容模型、传输包 |
| storage/evaluation | 578MB | 历史评测数据、模型副本与索引 |
| storage/incoming | 355MB | 上传来源、分片、封面候选 |
| storage/archive | 264MB | 正式原件，保护 |
| storage/public | 265MB | 正式阅读文件及衍生文件，保护 |
| storage/ocr-models | 146MB | OCR模型，保护 |
| 应用根offline等 | 约591MB及其他小项 | 原有离线构建依赖 |

当前archive/public没有被本次硬链接去重计数抵消，不可仅因名字相似就删除一份。原件、阅读副本和OCR衍生版本有不同职责。新统计命令会区分文件逻辑大小、同inode唯一大小和分配大小，并报告权限不足/超预算，而不把未读目录记成0。

Docker根目录为`/volume2/@docker`，在上表35.13GiB之外。全机Docker报告Images 50.67GB、可回收47.24GB；Build Cache 5.569GB；Volumes 4.608GB，其中可回收2.662GB。它们涉及共享层、回退镜像、测试数据库及其他应用，不能直接相加或把全部“可回收”当作本书库可删。

## 膨胀原因

1. `library-upload/codex-paddle-noavx-3.3.1-20260808`单项5.50GB，包含Paddle源码、Git历史、第三方依赖、数个build-noavx目录和编译缓存。其中build-noavx-r5约3.36GB。
2. 8月多轮2.6.0上传目录每份约0.73—1.45GB，包和解包结果同时保留。
3. 实际读取两个大型旧源码归档的成员目录，确认重复包含约440MB HuggingFace模型包、152MB旧升级包、150MB前端依赖包、121MB Paddle wheel和32MB旧ZIP。一个“源码备份”因此达到0.93—0.96GB，数次失败/重试又各留一份。
4. 31条BackupJob中已完成归档的记录字节总量约553MB；这与15.15GB的备份目录总量差别很大。原因主要是部署脚本保存的源码/回退目录，而不是数据库突然膨胀。记录量不代替逐个备份文件验证。

## 可以清理哪些

下表是候选与条件，不是已执行清理。实际清理仍需用户选择范围，先核对无进程使用、所需归档可恢复及清单散列。没有发现任一容器直接挂载library-upload；这不等于所有进程/脚本都已证明不依赖该目录。

| 优先级 | 准确范围 | 预计涉及空间 | 保留与核对条件 |
| --- | --- | ---: | --- |
| 优先 | `library-upload/codex-paddle-noavx-3.3.1-20260808/Paddle/build-noavx*`及同目录ccache | 约3.82GB | 先确认无编译进程；保留源码/补丁/构建说明及最终wheel。此处只是候选模式，执行时需展开成准确路径清单 |
| 优先 | `storage/models/discovery/.incoming-20260922-v308/models.tar.gz` | 671MB | 传输归档；完整模型目录已存在，但删除前仍核对归档散列/完整清单。现用`v308-fp32-v1`不动 |
| 次优先 | library-upload下旧2.2—2.6上传归档和解包目录 | 上限约17.74GB，含上两项中的Paddle部分，不能重复加总 | 保留必要离线依赖与最后有效构建产物，再按版本保留一份来源，删除明确重复/过时展开物 |
| 有恢复要求后 | storage/backups中的29个早期2.x/公开前快照目录 | 合计约10.64GB | 涉及历史回退，不建议一键全删；保留最新成功版本及必要历史里程碑，先迁移/校验再按准确目标删除 |
| 暂不动 | 当前3.0.8.1、3.0.8/3.0.7回退资料与最新正式DB备份 | 包含于15.15GB中 | 3.0.8.2正式上线并有新鲜备份/回退演练后再评估保留窗口 |
| 单独审查 | 停止且未挂载的旧评测volume、旧镜像与构建缓存 | Docker全机统计不能作为准确可删量 | 逐个确认归属和回退引用，不用系统级prune覆盖其他项目 |

Paddle repaired目录的wheel与当前`ocr_service/vendor`中的wheel已核对SHA256完全相同，均为`80d0ed4ce96859395cf634d4c3e06df4527ea2abdffc826f24b8f6bc68656f39`。这是最终二进制已有另一份的证据，不等于可以不保留补丁来源就删除全部编译工作区。

incoming约57MB是上传分片目录，但上传恢复状态/唯一来源尚未逐个核对，不作为立即可删项。evaluation约578MB包括旧模型/语料/评测记录，用户要求搁置精度分析并不意味着授权删除这些资料。

## 逻辑存储调整

- 3.0.8.2新增`scripts/package_release_source.py`，按准确Git提交生成源码归档，拒绝运行数据、模型、依赖、备份与旧归档等路径。基线1347个Git文件实际打包约4.57MB，相比0.93GB“目录全打包”显著缩小；不同源码版本大小不能视为严格压缩率对照。
- 3.0.8.2正式备份直接将不可变原件流式写入归档，不再先复制整份原件到暂存目录。数据库dump、manifest和校验仍保留；归档名称/恢复布局兼容。
- 模型/离线依赖固定一份经校验的版本目录，发布记录引用版本与散列。应用源码、数据库备份、构建缓存、临时传输物分开保存，避免相互包含。
- 建议保留“当前版＋上一成功版＋选定里程碑”，但本次不擅自设定自动过期删除。释放现有空间需要后续有范围的清理；优化代码不会自动让这些历史归档消失。

实际只读证据保存在受管工作区忽略目录`output/v3082/`：app_sizes、backup_sizes、library-docker-sizes、library-upload-sizes、storage-details、archive-contents、all-container-mounts、cleanup-retained-artifacts及Docker用量文件。初次API身份无法读取某些root备份目录，结果正确标为不完整；随后仅以root读取目录元数据/归档成员补全，未调整文件权限。
