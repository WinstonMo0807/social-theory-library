# 下一步整体架构与上架流程重设计

## 用户的实际要求

2026-09-13用户要求将当前已部署版本直接更新到原GitHub仓库默认分支，不再新建发布分支。仓库需要提供准确前后台场景，使后续GPT能够理解整个应用，并帮助重新设计整体架构，尤其是需要大幅修改的后台和上架流程。

本文件记录下一步设计任务，不表示已经选定新方案。本次Git提交只发布现状基线与说明，不在没有具体方案的情况下重写业务、换技术栈或迁移生产。

## 先取得共同事实

先读[实际架构](GPT_ARCHITECTURE_CONTEXT.md)、[上架与发布](INGESTION_AND_PUBLICATION.md)、[当前状态](CURRENT_STATE.md)和[AGENTS](../AGENTS.md)。然后沿资料中的定位核对源码，区分用户实际操作、后台领域规则、持久数据和可重建的派生结果。

不要将以下事情当作整体设计已经完成。

- 拆开CSS、React hooks或server-api，只证明部分代码职责更易维护。
- 改导航名称或把多个状态合成一个进度条，不能消除数据和权限差异。
- 有一个模型、API或Provider适配，不代表完整用户旅程已验证。
- 旧文档中的目标、历史测试数和演练状态，不能代替当前实现与真实生产。

## 优先回答的设计问题

1. 馆员最常见的完成单位是什么，是一份文件、一个出版版本、一个作品，还是一批待处理记录？如何在界面上保持身份明确？
2. 上传、手工书目、旧PDF复核和已发布维护能否进入统一任务视图？哪些差异确有必要，哪些只是历史入口遗留？
3. 保存、确认字段、预览、公开发布应怎样组织？是否需要自动保存、草稿历史或跨页面恢复，何时必须明确确认？
4. 用户希望单人完成上架还是强制双人审核？Editor、Administrator与Owner的权限怎样统一，特别是当前撤回入口不一致？
5. 书目可见、PDF可读、OCR可复制、全文可检索、语义/观点/问答可用分别怎样展示，哪些可异步完成？
6. 人工值、锁定值、候选、证据、拒绝与撤销怎样统一交互，而不把来源分组和置信度全部压给馆员？
7. 出版版本、替换PDF、局部OCR、页码、私人批注及历史URL如何迁移？失败后怎样回到稳定阅读？
8. Work、Edition、会话、编辑修订、公开修订及专业任务之间是否有职责重叠？先比较服务边界，再决定是否真的需要新表。
9. 知识编辑应围绕人物/概念等对象，还是围绕馆员待完成的任务？关系冲突、双学者档案和临时实体怎样人工处理？
10. 哪些系统异常应在当前工作台解决，哪些归Owner的处理中心？用户应该看到什么操作结果和可重试边界？
11. 哪些旧API、模型与样式可明确退役，观察与迁移完成后如何移除？兼容层应有证据和退出条件。
12. 若提出技术栈或基础设施变化，它解决了什么现有系统无法合理解决的问题？成本、NAS约束、迁移和回退如何证明？

这些是待讨论的问题，不应擅自默认用户已经接受自动发布、双人审核、云端永久存储、微服务拆分或新数据库。

## 需要交付的设计成果

先给能让用户判断的产品设计，再给工程设计。

| 成果 | 至少需要包含 |
| --- | --- |
| 场景与痛点 | 典型馆员/读者旅程、当前步骤、已经确认的问题、仍需用户确认的假设 |
| 新后台任务设计 | 页面组织、主要操作、预览、保存/发布反馈、错误恢复、批量与多版本场景 |
| 领域和状态设计 | 对象身份、数据所有权、状态转换、人工决定、公开资格、事务和权限 |
| 服务/API设计 | 哪些保留、收敛或替换；请求/响应契约、错误语义、幂等和并发约束 |
| 迁移设计 | 现有记录如何保留或映射、兼容期限、数据验证、回退和逐步切换方案 |
| 实施方案 | 按可用的用户旅程落地，明确完成标准，不用大量阶段名称掩盖未实现功能 |
| 验证计划 | 少而关键的真实流程，区分本地、PG、Worker、OCR/Provider和公网证据 |

可以提出一个推荐方案和必要备选，但不要仅给新目录树、空泛架构图或更换技术名词。请说明一本真实PDF从进入系统到读者找到并打开，管理员具体少做了什么、风险如何降低。

## 必须保留或明确迁移的资产

原始PDF、文件校验和历史版本、人工锁与确认关系、私人阅读数据、合法公开快照、页码与证据定位、既有URL、失败记录及审计、可恢复数据库备份和活动索引都不能为了重构方便直接删除或重建。

这不意味着现有每个表和函数都不能动。设计阶段可以提出重大变化；实施时必须说明如何保留这些业务资产，并在当前用户授权范围内执行。不要建立第二套需要长期手工同步的书库。
