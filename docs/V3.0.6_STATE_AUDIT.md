## 2. 不能忽略的关联语义

### 活动修订与公开URL

`publication_eligibility.py:28`的public_edition_q以及`:104`的active_catalog_snapshot都要求同一Edition、active状态和metadata_ready；全文另查fulltext_ready及DocumentRevision。该公开读取边界已有实现，不应重造第二份宽松资格规则。

公开列表与作品详情仍以主版本快照为主要内容。`WorkCardSerializer._public_catalog`（`catalog/serializers.py:615`）跳过非主版本，`WorkDetailSerializer.get_editions`（`:850`）另列所有合格版本。因此合法非主版本不能标成正在发布，也不能在不核对实际页面语义时生成伪成功链接。

`catalog_publication_state`目前每次重新get Edition（`:53`），`catalog_health`再次调用它；若列表逐行调用将额外查询。实施应让同一响应预载活动修订、草稿/任务摘要，计算函数不重复get或逐条检查NAS存储。列表读取不触发外部收费调用。

### PDF pending不是通过

文件三态还影响以下读取，不能只改FileBody：

- `ingestion/services/publication.py:169–183`预检仅拒绝normalized.invalid，没有pending分支。
- `catalog/services/field_decisions.py:315–323`以exclude(invalid)选择已就绪原件/规范文件，pending仍可成为字段正式值。
- `catalog/services/admin_workflow.py:592`及`:782`的文件/阅读步骤只拒绝invalid。
- `publication_commands.py:28`历史修订验证也只拒绝invalid。

建议新发布和恢复校验要求真实valid，并为pending提供等待/重新校验说明。不要为了显示绿色自动改Asset.validation_status，也不要借此批量改写历史数据或无证据撤下当前稳定公开内容。

### 现有文件历史不可重建

实际替换从`pipeline._finalize_item_publication`（`ingestion/services/pipeline.py:693`）建立同一Edition的catalog_updated事件，精确传入新content_asset_id及原替换来源。`knowledge_publication.py:1381–1391`在正式激活时移动当前文件选择，保留旧Asset和Page。

`pipeline._activate_replacement`仍有旧helper且会标记Annotation.orphaned，但当前pipeline调用的是事件路径而非该helper。不可把这个未调用helper当成当前替换流程事实或直接恢复使用。验证应通过真正的发布事件完成路径，检查旧公开版本直到新版本可用、旧Asset/Page及私人记录关系保持。

`ReplaceUploadItemView`现有校验包括上传类型/签名/大小、已发布目标、当前规范文件和活动替换任务检查，不能在Edition入口绕过。当前请求没有独立持久请求幂等键，新增入口需用既有任务/操作记录做重试识别及目标版本校验。

### 精确对象与会话

`maintenance_edition`（`work_editor.py:802`）明确edition参数时按Work归属筛选，不会退到其他Edition；省略时按主版本/年份/更新时间选首项。多版本的新维护界面应明确选择，不用省略参数掩盖选择不明。

`CatalogingSessionListView`（`cataloging_views.py:46`）另有前50条上限，不能靠抓这一个接口来假装全量统一待办。`cataloging_sessions.py:21`已有开放会话复用、request_key、Edition/上传锁与原来源保护，应复用而非创建平行任务表。

## 3. 统一只读响应建议

响应新增字段基于现有对象计算，不要求新增同名数据库表。保留旧字段时明确兼容期限，前端新实现只使用统一对象。

### 公开状态对象publication

| 字段 | 定义 |
| --- | --- |
| editorial_state | 原人工发布决定，不代表公开已生效 |
| public_state | unpublished/publishing/published/withdrawn；合法非主版本为published而非publishing |
| catalog_revision_active | 当前指针确属本Edition且active、metadata_ready |
| publicly_visible / listed_publicly | 保留旧列表可见语义：合法活动修订且is_primary；新版明确使用listed_publicly |
| active_revision_id | 合格活动修订ID；不合格指针放诊断字段而不冒充有效版本 |
| active_pointer_revision_id | 后台诊断原指针，注明无效原因，不进入公开API |
| fulltext_ready | 活动修订具有合法全文及DocumentRevision，不同于PDF可读 |
| public_url、detail | 仅返回符合真实路由语义的链接，并解释主版本/旧版服务/处理失败情况 |

work/edition/session/item身份、source_type、编辑草稿及基线、健康与权限在同一对象上下文返回。阅读文件、正文/全文、语义、观点和问答应保持独立，不增加总进度来覆盖不可用原因。

### 馆藏列表

原API继续支持q/view/document_type；增加真实page/page_size/total_pages/ordering，count/next/previous/results保留。Work模式保留primary_edition，并增加publication和health。Edition模式采用row_type=edition、id=EditionID、work_id/edition_id/is_primary/label、publication/health、assets/current_reader_asset。所有跳转使用行中实际Edition，不再从primary_edition猜目标。

### 待办与发布列表

统一参数为category（all/continue/attention/exception/publication_ready）、source、q、publication、page。默认集合是全量实际待办；scope=publication扩为所有Edition，使发布台能看到已发布、撤回与正在处理记录。

返回count/page/page_size/total_pages/next/previous/results及counts（all/continue/attention/exception/publication_ready）、ordering。旧首页continue_items等前12数组可以暂留，但必须由完整集合分类后得到，数量另读counts。每行包括稳定id（edition:UUID或upload:UUID）、source_type/session_id/item_id/work_id/edition_id/title/workbench_url/return_href、publication、health、步骤及真实问题数。

同一Edition的开放会话、上传及维护修订聚合到一个当前工作对象，来源历史仍可打开；无Edition上传单列，不伪造Work。全量分类需共享轻量判定与批量预取，不逐条构建完整工作台、读文件或触发处理。

### 6.3 明确切换主版本

源码审计找到Edition编辑策略已有is_primary，但没有协调当前/新主版本、并发、影响预览和原快照保护的操作入口。本轮增加`primary_editions.py`领域命令及`GET/POST /api/catalog/admin/editions/{id}/primary/`，复用原EditorialRevision、CatalogPublicationRevision、KnowledgePublicationEvent、投影任务和AuditEvent。

GET只读返回当前/目标身份、原公开修订、影响、受保护预览、完整版本指纹与一次请求键。POST要求原CanPublishWork权限、明确confirm、指纹及请求键。事务先锁Work再锁全部所属Edition；只允许选择已有合法活动公开修订的目标，未发布目标、坏修订、待发布草稿及人工冲突明确阻断。不会代替管理员发布目标草稿。
