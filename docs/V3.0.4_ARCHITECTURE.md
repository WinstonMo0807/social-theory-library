# Social Theory Library 3.0.4 编目与知识发布架构

本文记录 3.0.4 修改前的代码审计、取舍清单和实施后的数据职责。它以当前源码为准，不以旧交接记录代替代码事实。

## 1. 修改前审计结论

### 1.1 正式对象与关系

- `Work` 保存作品层身份。公开资格主要由 `Edition.state` 决定。
- `Edition` 保存当前版本的出版信息、文件处理状态和公开状态。它尚无稳定的正式馆藏 revision、metadata ready、fulltext ready 或活动智能版本指针。
- `Contribution` 直接连接 `Edition` 与 `Person`。当前 `approved` 同时承担人工确认和正式关系的含义，缺少草稿 revision 归属。
- `Person` 与 `ScholarProfile` 分别保存人物权威身份和公开学者页面。两者各有状态，发布时必须保持一致。
- `Discipline`、`Subdiscipline`、`Topic`、`KnowledgeNode` 和 `ReadingPath` 是规范知识对象。`TheorySchool`、旧 `Concept` 和 `WorkKnowledgeRelation` 仍是只读兼容层。
- `EditorialRevision` 已保护已发布 Work、Scholar、Topic、KnowledgeNode、Discipline、Subdiscipline 和 ReadingPath 的 JSON 编辑，但未形成统一 publication bundle，也没有稳定的公开索引版本切换。

### 1.2 候选采用的真实问题

- `accept_candidates_from_review()` 只在表单值已等于候选值后修改 MetadataCandidate 状态。它本身不写 Work、Edition 或 Contribution。
- Entity Resolution 的人物关联和新建草稿只创建 `approved=False` 的 Contribution。旧 Workbench 的正式作者只读取 approved 关系，因此会出现候选已经处理、作者仍为空。
- `save_workflow_section(confirm_section=False)` 仍直接改 Work、Edition、Contribution 和知识关系。它只跳过 FieldLock、候选 accepted 和章节决定。因此保存草稿与正式知识并未彻底隔离。
- `EditionWorkflowDecision` 是章节级状态。一个已确认章节可在作者为空时继续显示完成，因为作者为空只是 warning；候选状态又参与步骤指纹。完成度没有从字段决定动态推导。
- Field Enrichment 的 accept 对未发布对象直接改 canonical；QueryLexicon Candidate accept 会直接创建 verified alias。这些路径都可能在正式发布前触发派生词典更新。

### 1.3 派生系统边界

- QueryLexicon 已有 durable event、staging generation 和原子切换，但 registry 仍会构建草稿的 `admin_resolvable` 条目，且 Work 标题不在来源中。
- 全文、Semantic 和 Claim 文档带 `is_public`，公开查询也会再次检查 Edition published 和 Asset 资格。这些过滤应保留。
- 草稿与正式正文目前写入同一活动索引。索引文档没有正式 catalog revision，更新失败时无法完整保留上一稳定智能版本。
- `DocumentQualityAssessment` 已计算 fulltext、semantic 和 OCR 质量，但 OCR 成功后仍会直接公开全文索引并排队 Semantic。质量评估尚未成为 fulltext ready 门槛。
- Ask Library 只使用正式馆藏范围，不调用联网增强，也不会把历史回答当证据。它可继续复用统一 retrieval；需要补正式 revision 和 fulltext ready 资格。
- 观点检索已有多层公开过滤，但同样缺少 fulltext ready 和活动 catalog revision。

### 1.4 Admin 与预览

- Workbench 左侧可跳转，但 pending 章节不能编辑或保存，所以仍是强制线性流程。
- Workbench 将多类候选合并为全局集合，每个章节顶部都显示研究建议；候选数量和技术来源成为日常操作语言。
- Scholar、Topic、Theory、Knowledge Studio 和 ReadingPath 分别实现权威提示、字段增强、策展选择器、ReviewTask 和候选 Inspector。多处显示百分比、Claims、Projection revision 等内部概念。
- Dashboard 汇总四类候选表作为全局候选审核数量，并按 current step 判断可发布。
- 管理员作品预览已复用公开 `WorkDetailView`，这是正确基础；但 `/admin/preview` 仍被 AdminShell 包住，详情布局又只看浏览器宽度，导致侧栏占位后的内容被误判为完整桌面。

## 2. 处置清单

### 2.1 保留

- Django、Next/Vinext、PostgreSQL、Redis、Celery、Meilisearch 和 PaddleOCR。
- Work、Edition、Asset、Page、Passage、Person、Contribution 和规范知识对象。
- Evidence、DocumentRevision、DocumentQualityAssessment、EvidenceSpan、DerivedClaim 与 CuratedClaim 的来源分层。
- SafeWebFetcher、结构化来源适配器、FieldPolicy、ResearchFieldContract 和现有来源身份门槛。
- QueryLexicon 的 generation、staging、active pointer、归一化和幂等同步能力。
- DomainChangeEvent、CanonicalObjectRevision、ProjectionState、任务租约、重试和旧 revision 不覆盖新 revision的机制。
- EditorialRevision 对已发布对象的保护。
- Ask Library 的馆藏边界、公开 queryset 和 Evidence locator。
- 公开详情组件、受保护预览 API、PDF Reader、OCR 和索引服务。
- DecisionLog、AuditEvent 和拒绝反馈记录。

### 2.2 封装

- 将 EnrichmentCandidate、MetadataCandidate、EntityResolutionCandidate、QueryLexiconCandidate 和 TheoryReviewTask 封装为字段助手的内部来源。
- 将 Universal Entity Discovery 封装为馆内实体搜索和重复提醒，不向普通管理员显示来源分组与分数。
- 将 FieldPolicy 扩展为按字段选择 PDF/OCR、馆内实体、ISBN/DOI、正式书目来源、出版社资料和外部补充的策略注册表。
- 将 DomainChangeEvent 和 ProjectionState 放在正式知识发布事件之后，作为兼容消费者与运行状态基础。
- 将 Semantic、全文、Claim、推荐和 QueryLexicon 的现有任务放入字段影响映射，避免无关重算。
- 将公开 WorkDetail 和知识对象公开组件封装为公开页、紧凑工作台预览和完整草稿预览的共同渲染基础。

### 2.3 替换

- 用字段决定替换 EditionWorkflowDecision 作为完成事实。章节只聚合字段状态。
- 用事务化字段采用替换“先处理候选，再希望表单已经正确保存”的协议。
- 用 publication bundle 和正式 revision 替换保存时直接写 published/approved 关系的行为。
- 用字段级候选入口替换每节顶部的大面积候选面板。
- 用非线性导航和动态发布检查替换 pending 前置步骤门禁。
- 用知识发布事件和幂等消费者替换发布后同步直调 index 与各模块自行猜测数据库变化。
- 用管理员状态替换候选数量、worker 数量和 current step 组成的队列状态。
- 用容器宽度响应和无侧栏完整预览替换当前 viewport-only 管理员预览。

### 2.4 废弃

- 普通后台的全局候选审核中心入口。底层数据和诊断查询保留。
- 普通 Workbench 中的 QueryLexicon、Authority、Semantic、Projection、Worker、Claim Index、source score 和百分比展示。
- `confirm_section` 作为字段完成或可发布的事实来源。接口只在过渡期兼容。
- 候选 accepted 即表示正式字段完成的旧假设。
- 普通页面的含糊责任者标签。底层 Contribution 保留，界面使用作者、译者、主编、编者、校注、摄影和其他贡献者。
- 对任何 Work 或 Edition 变化统一刷新所有投影的粗粒度影响映射。
- 已发布维护流程中的同步 `index_asset(is_public=True)` 直调。

### 2.5 需要迁移或审计

- accepted candidate 但目标字段、Contribution 或知识关系为空。
- Candidate 状态与正式关系、FieldLock、章节决定不一致。
- 重复 Person、Topic、KnowledgeNode 和 PublisherAuthority。
- 已发布 Edition 缺少公开全文、Semantic 或 QueryLexicon 派生记录。
- 草稿或未确认别名进入 QueryLexicon generation。
- 草稿 Edition 或低质量 OCR 进入公开全文、观点检索、Ask 或 RAG 来源。
- 已发布知识关系仍只存在 legacy 表，或 normalized 与 legacy 状态冲突。
- 历史正式馆藏建立初始 CatalogPublicationRevision。迁移只回填可证明的状态，不自动合并、删除或改写人工馆藏。

## 3. 三层数据职责

### 临时证据层

保存 OCR 初步结果、联网资料、权威来源、AI 候选、候选图片、外部摘要、未采用和拒绝反馈。它只帮助判断。

### 正式馆藏层

保存管理员确认并正式发布的对象、字段、关系、别名、正文和说明。CatalogPublicationRevision 记录一次可审计的正式快照。它是唯一事实源。

### 派生智能层

保存 QueryLexicon、全文文档、Semantic passages、观点索引、Ask/RAG 可检索材料、知识关系读模型、推荐和缓存。它必须能从正式馆藏重建，不能反向写事实。

## 4. 3.0.4 核心对象

### CatalogFieldDecision

每个编目上下文和字段只有一个当前决定。状态包括 empty、suggested、needs_review、confirmed、conflict、not_applicable 和 stale。它记录当前值、来源摘要、依赖指纹、人工确认者、候选引用及更新时间。

管理员修改上游字段时，未确认的下游建议可以失效。已确认字段只标 stale，不自动删除或覆盖。

### PublicationBundle

一本作品及编目中即时创建的人物、主题、理论节点或出版社可以归入同一 bundle。保存只保留草稿。发布前检查 bundle 中每个对象的最低完整性和重复提醒，发布时一起 materialize。

### CatalogPublicationRevision

每次首次发布、正式更新、撤回和正文版本切换都产生单调 revision。revision 保存正式快照、变化字段、DocumentRevision、metadata ready、fulltext ready 和处理状态。旧活动 revision 在新正文相关投影准备失败时继续服务。

### KnowledgePublicationEvent

事件覆盖 catalog published、updated、withdrawn，以及 entity published、updated、merged。事件在正式数据库事务内写入，提交后由幂等消费者处理。每个消费者单独记录状态和错误，重复执行不能制造重复条目。

## 5. Field Assistant

字段助手接收当前对象、字段、已确认上下文、馆内正式知识和字段策略。返回的普通管理数据只有候选值或实体、建议采用、需要确认或存在冲突、证据摘要及可执行操作。

候选按规范化字段值和实体身份聚合。多个来源支持同一人物时只返回一项。默认最多三项，更多结果由字段内展开。原始 confidence、authority score 和 source score 只出现在系统诊断。

字段策略至少覆盖以下优先级。

- 作者和译者优先当前 PDF/OCR、馆内 Person、ISBN 或正式书目，再使用外部补充。
- 出版社和本版年份优先版权页、ISBN 和馆内规范实体。
- 封面优先当前 PDF，再按 ISBN、书名、作者、出版社和年份匹配同版本。
- 简介优先 PDF、出版社和可靠馆藏介绍。AI 整理必须标 provenance，确认前不得进入正式知识。
- 学科、主题和理论使用获取分类建议，优先馆内规范节点，只在确无匹配对象时建议新建。

## 6. 保存、采用与发布

字段采用必须在一个数据库事务中完成候选锁定、实体匹配或草稿创建、草稿字段或关系写入、CatalogFieldDecision、候选状态、依赖失效和审计。任一步失败则全部回滚，界面显示未保存成功。

保存草稿不产生正式知识发布事件，不增加正式 QueryLexicon，不激活公开全文、Semantic、观点检索、Ask/RAG 或推荐。

正式发布先验证必要字段、文件、阻断冲突、bundle 新实体和重复风险，再 materialize 正式对象并建立 CatalogPublicationRevision。事务内写 KnowledgePublicationEvent，提交后才运行派生消费者。

## 7. 字段影响映射

| 变化 | 受影响消费者 | 不应执行 |
| --- | --- | --- |
| 封面 | 公开详情、图片缓存 | OCR、分块、embedding |
| 出版社、年份、ISBN | 书目搜索、全文文档 metadata、Ask/RAG metadata | OCR、embedding |
| 作者和人物别名 | 人物关系、人物搜索、QueryLexicon、书目与 Ask/RAG metadata | OCR |
| 主题 | 主题关系、筛选、推荐、Ask/RAG metadata | OCR、embedding |
| 理论传统或节点 | 知识关系、推荐、Ask/RAG metadata | OCR、embedding |
| PDF 或 OCR 正文 | 分块、全文、Semantic、观点检索、Ask/RAG 正文 | 无关图片处理 |
| 撤回 | 全部公开派生消费者移除或失活 | 删除原始文件与历史 revision |

## 8. OCR 与公开正文

metadata ready 允许作品先公开书目和 PDF 阅读。fulltext ready 需要活动 DocumentRevision、达到配置门槛的 fulltext/semantic 质量和完整引用定位。OCR 未完成或质量不足时，正文不进入公开 Semantic、观点检索和 Ask/RAG；管理员可以看到重新处理入口。

## 9. Admin 契约

- 左侧文件、作品、版本、作者、学科、理论、主题、发布只作导航和推荐顺序。
- 所有字段可任意顺序编辑。章节完成度由字段决定聚合。
- 字段旁提供智能查找、重新查找、获取分类建议或查找其他封面。
- 队列只显示待审核、存在冲突、信息不完整、可以发布、发布处理中和发布后异常。
- 技术任务、模型、分数、stack trace 和 index revision 只在系统诊断。
- 紧凑预览位于 Workbench 内。完整草稿预览不显示 Admin 侧栏，只保留薄工具条，并复用公开详情组件。

## 10. 兼容与回退

- 旧正式 Work、Edition、Person 和知识关系保持原 ID 和可读性。
- 初始 migration 只建立新表、字段和可证明的 revision，不自动处理重复实体。
- legacy TheorySchool、Concept 和 WorkKnowledgeRelation 在 parity 审计通过前继续只读。
- 派生消费者失败不回滚已提交的正式馆藏；旧活动智能 revision 保留，管理员可重试。
- 用户已授权完成后推送与公网升级。生产操作仍须满足 fresh backup、PostgreSQL 16 恢复演练、migration plan、回退镜像、空闲任务窗口和公网验收；授权不包含未经规则的历史数据批量修复。

## 11. 当前源码映射

- schema 位于 `api/catalog/models.py` 与 `api/catalog/migrations/0040_v304_cataloging_intelligence.py`。
- 字段决定、依赖与发布检查位于 `api/catalog/services/field_decisions.py`。
- 统一字段助手位于 `api/catalog/services/field_assistant/`，管理员入口位于 `api/catalog/field_assistant_views.py`。
- 正式 revision、publication bundle、知识发布事件和消费者投递位于 `api/catalog/services/knowledge_publication.py`。
- 公开资格统一位于 `api/catalog/services/publication_eligibility.py`，由公开 serializer、全文、Semantic、观点和 Reading 服务复用。
- 正式词典规则位于 `api/catalog/services/query_lexicon/registry.py` 及相邻 sync、resolver 和 operation 模块。
- 只读历史报告位于 `api/catalog/services/catalog_consistency_audit.py`，命令为 `audit_v304_catalog_consistency`。
- Workbench 字段入口位于 `web/components/admin/workflow/field-assistant-control.tsx`。普通策展页面的适配位于 `web/components/admin/curation/`。
- 完整作品草稿预览和公开作品页共同使用 `web/components/work-detail-view.tsx`。

当前实现状态与没有验证的范围见 [V3.0.4_REQUIREMENTS_MATRIX.md](V3.0.4_REQUIREMENTS_MATRIX.md) 和 [V3.0.4_UPGRADE.md](V3.0.4_UPGRADE.md)。
