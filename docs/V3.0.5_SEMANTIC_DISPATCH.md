# 语义任务投递失败保护

状态为本地实现与受控测试通过，尚未部署。

完整 Reader/文件替换回归发现 `dispatch_semantic_job` 在队列投递失败时，无条件将任务引用的 SemanticIndexVersion 改为 failed。普通增量任务也会引用活动版本，因此一次 Redis/传输故障可能让系统失去活动索引指针。没有物理删除索引，但会影响后续任务查找活动版本。

本次修改只允许未完成候选（building/ready）被该失败标记影响。活动版本和保留的回退版本保持所有既有元数据不变。任务与所属 Edition 仍记录失败，原任务和错误不删除，既有恢复机制仍可重派。

失败写入使用 queued 状态和准确 task_id 进行条件更新。更新成功才继续记录 Edition 和候选版本失败，并在一个数据库事务内完成。如果 Worker 已开始/完成，或恢复流程已换用新的 task_id，迟到的旧投递错误不能覆盖这些新状态。网络投递本身不持有数据库事务。

## 验证

- `test_semantic_dispatch_safety_v305.py` 首次 active/building 两组为 1 failed/1 passed，复现活动版本被误改，78.33 秒。
- 修复后同文件与 `test_durable_pipeline_dispatch.py` 合计 12 passed，退出 0，87.57 秒。
- 新用例覆盖 active、retired、building、ready，及已完成任务/新 task_id 对迟到错误的隔离。
- 模拟异常发生在 Celery apply_async 边界。不调用实际 Redis、Meilisearch 或模型，不证明生产连通性，也不证明真实 PostgreSQL 并发锁。

回退源码不会恢复曾被误标的生产数据。生产如存在类似记录，应先只读审计实际索引、任务与版本状态，取得明确修复授权后再处置，不能自动重建或直接更新生产表。
