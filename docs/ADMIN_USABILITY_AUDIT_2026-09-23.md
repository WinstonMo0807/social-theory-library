## 管理对象的完整操作

用户已确定：错误上传可恢复地移出待办；学者、理论流派、主题等所有同类对象都提供删除入口；删除与下架明确分开。

不能只把现有 DELETE 接到新按钮：上传的删除主要归档流程记录，入口隐藏在处理中心二级位置且权限很窄；部分学者/主题 DELETE 转为下架草稿，部分未发布规范对象却可能永久删除。下一版要先统一接口与数据语义。

| 操作 | 结果 | 恢复规则 |
|---|---|---|
| 保存修改 | 保存明确选择的编辑范围 | 保留修订与冲突检查 |
| 下架 | 停止公开展示，正常后台列表仍保留 | 经原发布检查重新上架 |
| 删除 | 移入回收站，从正常列表、待办、新关联候选中移出 | 可恢复；恢复不会自动重新发布 |
| 取消处理 | 结束这次后台工作，保留对象和已完成页 | 明确继续或重新提交 |
| 合并 | 确认身份后归并引用，保留来源历史 | 按合并记录撤回；不等于删除 |

已公开对象点击删除时，预览明确写“下架并移入回收站”，由一次明确确认完成必要撤回。独立的下架按钮继续保留。回收站按类型筛选、搜索、恢复及查看原因，不自动清空；原 PDF、人工确认、历史版本、原文定位、读者笔记和审计不硬删。

覆盖清单包括上传/待办、作品/版本/文件、人物/学者、学科/子学科/流派与知识节点、主题/出版社、关系/时间线/阅读路径、策展/推荐期与计划项、网站内容，以及其列表、详情、编辑页和选择控件。各类对象保留权限边界；无权限时说明原因与后续入口。

选择控件的“移除此关联”只影响当前对象，必须与全馆“删除对象”分开。删除学者展示页不能级联删除作者/译者身份。有引用时展示影响数量和关系，保留历史身份；需要改配的有效关系提供替换/合并，不静默清除。不能修一个示例页面后宣称全后台统一。

错误上传在列表和详情直接提供修改资料、替换文件、删除。替换创建新文件版本，保留旧原件与人工书目。运行任务处理取消意图与版本校验，迟到结果不能让已删除记录重回待办。

## 图 1：系统错误不能归咎于 PDF

截图与现网失败记录一致：`catalog_passage.normalized_text` 的 B-tree 索引项超长。当前 `Passage.normalized_text` 为 `TextField(db_index=True)`，初始迁移已存在这一索引，并非新观点引擎才引入。

PostgreSQL 对 B-tree 单项大小有约数据库页三分之一的限制，长段落可能触发它，见 [PostgreSQL 16 官方说明](https://www.postgresql.org/docs/16/btree-intro.html)。重新上传同一 PDF 并不能解决该数据库问题。

建议核对实际查询用途，通过 Django migration 移除或替换不适合长文本的普通 B-tree，同时审查其他同类文本列。全文匹配沿用已有检索职责，不通过截短原文、丢段落或破坏字符偏移规避问题。修正后只重试受影响派生环节。

界面先解释“系统保存全文失败，原文件已保留”，完整技术异常放在详情。PDF 格式错误、OCR 超时、数据库写入失败分别给出处理路径。

## 封面与书目信息

当前正常文档已经有保存并确认的 PDF 第 1 页封面，文件存在，记录时间为 2026-09-22 10:09 香港时间。不能据此否定此前失败，也不能把当前状态写成始终没有封面。

源码中有两条明确风险：封面选择/上传被整页任意未保存修改阻止；封面指纹包含作品更新时间，保存其他资料会改变它，但封面子组件不随这次保存刷新指纹，下一次操作可能遇到 409。历史失败具体是否走了这些路径，仍缺 HTTP 证据。

下一版让封面成为独立保存范围：选 PDF 页或上传图片后预览，显示尚未保存、保存中、已保存；只保存封面，不强迫先提交全部书目。冲突检查绑定封面修订及来源文件，保留本地选择，服务端成功但响应丢失时可找回回执，不重复上传。不取消并发保护。

书名、出版社、作者与译者的自动提取继续作为建议，人工值优先；没有可靠结果时允许直接填写并说明原因。图 1 的推广文字混入题名提示需加强候选过滤和来源展示。ISBN 统一输入并校验 10/13 位；仅有年份时不补造 1 月 1 日。无需自动访问外部书目来源。

## 提示、作者与译者

现有提示已经有点击跳转逻辑，但缺准确字段和醒目反馈。作者与译者分组后重新从 0 编号，产生重复定位；选择人物时更新的是 `items`，旧错误却是 `items.0.person_id`，现有错误清除逻辑匹配不到。

下一版问题记录使用稳定行标识、字段、严重程度、处理动作。点击后展开、滚动、聚焦、对应边框与文字提示，不只靠颜色。输入修改后即时重验；上次保存状态与本次未保存状态分开。红色表示必须修正，黄色表示建议检查且能明确继续，中性提示表示等待内容确认。“尚未确认”不应伪装成“填错”。

人物部分还确认了以下问题：

- 新建人物回填保留有姓名但未关联的原行，再追加一行关联，原行继续阻止操作。
- 人物选择用学者列表接口，新建作者/译者也建学者资料草稿，将身份与公开介绍绑在一起。
- “新建”藏在填写建议中，人物创建与本书关联分两次保存，成功范围不清。
- 下拉打开时会查询，带 180 毫秒延迟，但创建成功没有统一刷新其他已打开的选择器。
- NAS 确有两个郑作彧草稿，创建相隔约 26 秒，并非只是重复渲染；没有两次请求日志，不能断言唯一原因就是双击或延迟。

建议每一作者/译者行直接显示“选择已有 / 新建人物”。新建填回当前行；查找同时展示姓名、原名、别名及必要辨别信息；译者不必先完善或发布学者页面。新建的最小身份与书目关联在本节显式保存时作为同一可重复安全提交的操作，超时可查回执、重试不重复创建。相同姓名只是查重线索，不自动合并。

保留人物身份关联能力，但由行内操作完成，不要求上传者理解内部规范库。离开时提醒未保存，不悄悄自动保存其他表单。

人物查重应提供保留对象选择、引用影响预览、冲突处理、合并历史与撤回。当前合并受所有者权限限制；管理员可直接合并还是提交所有者，已询问用户，尚待回复。删除无用草稿与合并有引用人物分别提供，不用删除绕过身份冲突。

## 学者展示与长文布局

首页卡片显示中文展示名和已有外文原名；缺失时不编造，常见译名通过别名管理和检索使用，不擅自替换中文首选名。

重要文献改为随容器宽度变化的卡片/列表，封面与题名在顶部，简介在下面使用完整宽度；默认约 3—4 行，提供展开及查看文献，空简介不撑高。保留黑白暖灰、现有字体和页面风格。共享卡片采用明确展示模式，避免学者页改动破坏首页与检索结果。

### 执行和反馈均有缺口

1. 当前 OCR HTTP 等待为 3600 秒，运行任务停滞恢复门槛为 1800 秒，排队恢复门槛为 180 秒。
2. 停滞判断使用 `started_at`，识别调用中没有持续任务心跳，正常慢调用可能被重新派发。
3. 恢复更换任务标识并重新计尝试；旧任务的迟到结果因标识保护不被接收。迟到保护需要保留，但错误恢复会浪费计算。当前失败任务也有排队恢复记录，完整尝试因果顺序尚未重建，不把机制风险写成每次失败的唯一原因。
4. OCR 单进程池串行执行，整批返回后才保存；缺可查询的服务端排队/页内阶段回执。
5. 专用 OCR 控件约 2 秒查询，处理中心大列表约 15 秒查询。旧任务首批完成前可能没有可靠页数；超过 90 秒无更新只说“当前页尚未返回”，不能区分正常慢页、排队和失联。
6. 健康接口响应不代表一本书持续处理成功。当前上传记录 ready/100% 与关联 OCR 失败可以并存，应明确显示不同阶段。

### 下一版方案

保留现有架构，补充稳定任务/文件版本/页批请求标识，服务端排队与执行回执，可续期的任务占用凭证和心跳。真正丢失心跳才恢复；重试先查回执，排队不消耗识别失败次数。逐页保存，失败只影响未完成页；入队即确定目标页数；取消后拒绝迟到写入。

管理员直接看到已保存页数、当前页/排队位置、最近心跳、最近完成页时间、当前阶段用时、失败保留结果及下一步。区分页面连接正常与任务没有心跳；没有实际页内比例时显示阶段，不伪造百分比。暂停、继续未完成页、重试失败页和取消在同一任务卡上可见。

资源侧测量后设预算：OCR 与全库索引回填错峰/限并发，交互检索优先，避免重复加载模型；用真实代表页比较线程、分辨率、模型配置，同时检查识别质量。不能盲目压内存上限造成 OOM，也不能无限延长超时。保留其他 NAS 项目，不关闭 swap 掩盖问题，不启用付费 OCR，不要求另一台电脑常开。

## 追加：只优化 API 与观点检索推理容器，性能不得下降

用户进一步明确，图 9 重点是 API 与 discovery-inference 的运行内存，要求不损失当前性能，最好同时提升性能。这作为优化的验收约束，不预先承诺未经测量的降幅或加速比例。

补充只读检查显示 API 有 3 个 Gunicorn 业务进程，Compose 的实际入口未开启应用预加载；Dockerfile 中的线程配置被 Compose 启动命令覆盖，不能按 Dockerfile 猜现网并发模式。3 个业务进程的 PSS 分别约 93、57、90 MiB，SwapPss 约 135、168、265 MiB，进程还存在已换出的私有内存。测量脚本自身的临时 Python 进程不计入业务进程判断。PSS 按比例分摊共享页，不能与 Docker 列表数值混用，也不能只看 RSS 下降就宣称节省。

推理服务只有一个 Uvicorn 进程，PSS 约 669 MiB，另有约 200 MiB swap。源码已经限定只保留当前模型/分词器，并关闭 ONNX CPU arena 和 memory pattern；因此“关闭缓存”“少开一个模型”不是未做的新优化。固定 FP32 embedding 权重文件本身约 448.5 MiB，磁盘权重大小不等于运行占用，但表明 700—800 MiB 不能直接认定异常或泄漏。

优先评估以下不改变功能与质量的方向：

1. API 保持现有业务进程数，实验预加载后写时复制共享只读代码/数据，核对 fork 后数据库/HTTP 连接、锁与后台线程安全。Gunicorn 官方明确说明预加载可能减少内存，但对本项目的净收益仍需测量：[Gunicorn preload_app](https://docs.gunicorn.org/en/stable/settings.html#preload-app)。排查重复常驻数据、大查询结果完整物化和响应中间副本；减少这些冗余不需要减并发。
2. 推理保持现有模型、FP32、文本长度、候选范围、重排与线程配置，检查无用数组副本、过长对象生命周期及模型切换后的分配器碎片。ONNX 官方提供分配器优化方向，但本服务当前单会话且已禁用 arena，不能照搬多会话共享 arena 的建议：[ONNX Runtime 内存说明](https://onnxruntime.ai/docs/performance/tune-performance/memory.html)。更换分配器只作为隔离候选实验，兼容性和实测不过不采用。
3. 不用定时重启、空闲强制卸载当前模型、降低精度/候选数、减少 worker 或把内存挤入 swap 达成表面数字下降。也不移除这两个现网必要服务。

基准需采用同一数据/模型/硬件和可比后台负载，覆盖启动首请求、热请求、交替编码与重排、普通/扩大检索、多请求并发、后台 OCR 同时运行。分别测常驻及峰值 PSS/cgroup 内存、swap、CPU、延迟分位数、吞吐和错误率；核对返回内容、排序及数值输出是否保持原契约。重复对照以识别测量波动，不能以一条快查询证明所有性能完全无损。任何确认的时延、吞吐、质量或稳定性退步都不通过；暂时找不到符合约束的降幅时保留当前配置并如实报告。

当前判断：API 的多进程重复加载值得优先实验；推理已经采用较紧的驻留策略，可优化空间尚不能量化。减少真实冗余可能同时减少换页并加速，但这是待验证收益，不能先报成功。本轮没有调整这两个容器配置，也没有在繁忙生产机上发起压测。

## 完整交付的实施与验收范围

内部先修长文本索引及 OCR 执行协议/资源调度，再完成统一生命周期、人物与封面编辑闭环、错误定位，最后统一状态呈现和公共卡片。作为一次完整改进交付，不拆成要求逐项批准的开发阶段。

全部实现后集中验收，仅复跑失败与受影响项：

- PostgreSQL 长段落实际写入与迁移演练，原文和偏移不截断。
- 错误上传删除/恢复/替换，运行中取消和迟到回写，人工资料及原件保留。
