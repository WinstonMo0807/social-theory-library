# 后端架构与性能审计

日期：2026-09-27。源码基线：`main / 14a41a1`。范围：先读代码，再做隔离实验和横向比较；不修改应用实现，不连接生产，不调整权限、数据库或索引。

## 判断

当前最值得优化的是重复计算与跨服务 I/O 的粒度。已有架构并不需要为了采用算法而换成微服务、图数据库或新的树结构。应优先处理后台队列的重复表达式、检索结果重复水合、索引逐段提交，然后根据测量决定更深的结构变化。

这里的“水合”指根据结果 ID 重新取出正文、关联元数据并校验可见性。当前权限和修订校验有业务必要，优化不能把它们整体删除。

优先级表示建议调查和实施顺序，不是生产故障等级；没有生产延迟、CPU、磁盘或锁等待的本轮测量。

| 顺序 | 发现 | 证据等级 | 建议 |
| --- | --- | --- | --- |
| 1 | 后台队列反复生成复杂 SQL，且分页没有限制关联历史数量 | 当前 ORM 实测 | 减少重复统计和表达式展开；只取列表需要的当前任务/修订 |
| 2 | 检索分页前校验全部候选，另有全馆范围计算 | 当前 ORM 实测；大规模范围为合成输入 | 分开轻量可见性/状态检查与正文读取，保留即时撤权 |
| 3 | 索引逐段提交、逐段等待外部任务完成 | 当前写入函数调用计数，外部服务替身 | 比较小批量写入；保留逐批成功确认、幂等和修订保护 |
| 4 | 原文重叠去重遍历全部已保留结果 | 当前函数与原型 A/B 实测 | 先用文件和页码分桶，不急于引入区间树 |
| 5 | OCR 每完成一页反复重读/重建剩余页面集合 | 当前辅助函数实测 | 保留每页落库，减少调度元数据扫描 |
| 6 | 子学科树逐层回查祖先 | 当前校验与邻接表原型实测 | 浅树可保留；深树比较批量邻接表与递归 CTE |
| 待定 | 两类推理模型轮换、所有推理入口共享锁 | 当前源码确认，运行影响未测 | 先量化换载、等待和峰值内存，再决定调度或常驻策略 |

## 已核实的架构与合理边界

请求通过 Django 读写 PostgreSQL，Celery 承担后台处理，Redis 承担缓存和消息，Meilisearch 保存可重建的检索投影；OCR、Discovery 推理各有独立服务。当前 Compose 为 Discovery 查询和索引设置独立队列，但它们共享同一个推理服务。这是源码/配置事实，不是本轮生产容器观察。

Work → Edition → Asset → Page 表达不同身份；DocumentRevision 与 CatalogPublicationRevision 分开保存文本解释和正式公开版本。知识关系是图，子学科 parent 是树形邻接关系，不能将全部业务实体强行改成一棵树。

以下措施应保留：

- `public_editions()` 校验活动修订的归属、状态及正文资格；结果返回前还会复核来源和原文片段。
- `save_workspace_edits()` 在事务中按既定顺序锁定对象，校验编辑版本和请求回执。不能以性能优化为由删掉这些保护。
- 索引写入在外部任务成功后才标记 ready，旧任务用 task_id/修订校验隔离。
- OCR 每页成功后保存，故障可以继续；书目公开与全文可用分开。
- 管理列表已经先分页再加载馆藏，且多处采用预加载。不能再将历史“全库工作台逐项加载”作为当前缺陷。
- 搜索任务已经复用原查询向量；候选上限为每通道 400。不能把无上限的理论复杂度当作当前一次请求的真实规模。

源码依据：[公开资格](../api/catalog/services/publication_eligibility.py)、[整页保存](../api/catalog/services/workspace_edits.py)、[Discovery 会话](../api/catalog/services/discovery_sessions.py)、[任务写入](../api/catalog/services/discovery_indexing.py)、[配置](../compose.discovery.yaml)。

## 1. 后台队列：表达式重复比单纯缺少索引更值得先处理

`admin_queue_query.py:26` 的 `edition_inventory()` 用多层 `Exists/Case` 计算业务状态。后面的分类条件再次引用这些表达式时，生成 SQL 中出现大量展开。`queue_page():161` 又执行分页总数、五类数量、四类预览和当前页查询。

在当前模型的内存 SQLite 上创建 67 本纯书目馆藏，读取第 2 页：

| 指标 | 结果 |
| --- | --- |
| 返回馆藏数 | 30 |
| SQL 语句数 | 31，其中 COUNT 查询 6 条 |
| 最长 SQL | 56,883 字符、183 处 `EXISTS(` |
| 单次本地总耗时 | 1,592 ms |
| 单独 cProfile 观察 | 总 3.364 s，`compiler.as_sql` 累计 2.859 s；剖析本身增加开销 |

这表明在该样本里，ORM 编译重复表达式本身就很贵。`EXISTS` 出现次数不是数据库实际扫描次数；PostgreSQL 可能采用不同计划，不能从这些数字推出生产执行计划。

横向实验仅比较五类计数，使用同一 67 本夹具、无未绑定上传项：

| 方案 | 查询数 | 单次耗时 | 取舍 |
| --- | --- | --- | --- |
| 当前分别统计五类 | 5 | 679 ms | 多次编译相近逻辑 |
| 条件聚合一次统计 | 1 | 304 ms | 数量完全一致，但 SQL 增至 108,080 字符；还不是完整队列替代实现 |
| PostgreSQL 分层子查询/必要时物化 CTE | 未测 | 待核实 | 尝试让基础状态只计算一次；必须检查计划，物化也可能阻碍条件下推 |
| 持久化队列读模型 | 未测 | 待核实 | 读快，但要承担事件更新、重试和一致性成本，仅在前两种不足时考虑 |

另一个独立问题在 `admin_queue.py:26`：`processing_jobs`、`cataloging_sessions`、`catalog_revisions` 等被全量预取。为单本夹具增加 2,000 条历史处理任务后，即使只请求 1 本，也加载了全部 2,000 条任务。馆藏分页限制不能约束每本的历史长度。应将列表需要的最新任务/失败状态与历史详情读取分开，保留历史原记录。

## 2. 检索：展示范围小，重复校验范围大

调用链为 `discovery_views` → `serialize_session()` → `_rehydrate()` → `validate_discovery_results()`。当前先水合全部候选、读取对应正文并验散列，再切出当前展示页；随后 `discovery_coverage()` 又计算当前范围的覆盖。前端运行中首次约 1.5 秒后轮询，此后在前次请求结束约 2 秒后再读，完成后停止定时轮询，另有可见性刷新。

同一正式来源的合成短文本，固定返回 3 段；时间为无并行干扰的一次复测中三次中位数：

| 会话候选数 | 实际返回 | 正文散列校验次数/请求 | SQL 数 | 本地中位耗时 |
| --- | --- | --- | --- | --- |
| 3 | 3 | 3 | 7 | 22.1 ms |
| 60 | 3 | 60 | 7 | 30.3 ms |
| 200 | 3 | 200 | 7 | 50.9 ms |
| 400 | 3 | 400 | 7 | 76.9 ms |

查询数没有增长，但取回的文本量和 Python 工作量随候选数增长。这就是只统计 SQL 条数会漏掉的问题。复杂度按每次请求为 O(K·L)，K 为候选数，L 为候选原文长度；不会因页面仅显示 3 条自动变成 O(3·L)。当前执行检索时，候选获取函数已经水合一次，`execute_session():381` 又作一次校验，也存在同一任务内复用的候选空间。

建议比较两个层次：

- 小改动：运行状态和结果版本未改变时走轻量状态读取，正文列表按需加载；当前请求内复用已读取的来源元数据。仍要处理权限、撤回、正文变化，不能仅以会话 updated_at 判断来源没变。
- 进一步改动：以来源/修订/权限状态做批量资格筛选，再按稳定结果位置分批取正文，遇到撤回结果补齐下一条。当前 `count` 是精确可见数量，优化必须保留或明确调整这个契约；简单先切 3 条会破坏过滤后的分页和计数。

不建议直接给整个公开响应加固定 TTL 缓存，因为当前测试明确要求撤回、权限降低和原文变化在下一次读取时生效。

### 全馆范围也是增长限制

`current_scopes()` 枚举所有当前合法来源，组合 `scope_token IN [...]`，放进关键词和向量请求。无筛选的 edition 路径已经使用轻量 `values_list`，但仍为 O(N)。覆盖统计也有 O(N) 遍历；带其他筛选时要构建来源 header 后在 Python 检查。

用合成 UUID 和 64 字符修订号调用当前范围函数，未连接 Meilisearch：

| 合法版本数 | 仅该 filter 字符串字节数 |
| --- | --- |
| 1,000 | 113,015 |
| 10,000 | 1,130,015 |
| 20,000 | 2,260,015 |
| 20,001 | 抛出 `scope_limit` |

这是确定的实现上限，不是已经发生的生产容量故障。不能简单删除上限或只做命中后过滤：失效旧文本即便最后被剔除，也可能先影响召回排名。长期可比较版本化的可见性投影、按权限/修订分组的检索过滤，或有严格刷新机制的范围缓存；这些均需撤回并发和索引滞后验证。

## 3. 索引：每段都完整往返一次

`discovery_indexing.py:296` 的 `_write_chunk()` 每段检查任务/修订、查旧向量、单段请求 embedding、写 ORM、单段提交 Meilisearch、等待任务，再确认 ready。`wait_index_task():71` 在任务未完成时每次睡 0.3 秒；不是无条件每段都睡 0.3 秒。

调用真实写入函数处理 12 个不同的新片段，只将外部 embedding 和 Meilisearch 换成计数替身，首次状态查询即成功：

- embedding 请求 12 次，文档提交 12 次，状态查询 12 次。
- SQL 252 条，包含事务及 SAVEPOINT，不能写成 252 次业务 SELECT。
- 没有测量真实模型、网络或 Meilisearch 的吞吐。

优先比较“推理仍按受控大小执行、索引按 8/16/32 段组成小批次提交”的方案。批量大小只是下一轮测试变量，不是已选最佳值。若每批 B 段，外部提交及成功确认的次数可由 C 量级降为 ceil(C/B)；模型计算和实际写入的数据量不会随之消失。

每批仍须携带确定 ID、同一来源修订及任务身份，外部批次成功后才确认 ready；失败重放、撤回、换修订和崩溃恢复要覆盖。既有逐段检查点、全局 writer 锁都是保护机制，不能为了减少语句直接移除。[Meilisearch 官方批量写入建议](https://www.meilisearch.com/blog/best-practices-for-faster-indexing)也强调分组提交，当前逐条等待限制了这种收益。

`discovery_projection.meili()` 与推理客户端每次新建 `httpx.Client`，连接池不能跨调用复用。可作为批处理后的第二项小实验，但本轮没有网络握手成本数据，也不建议直接在 Gunicorn preload 前创建跨进程共享客户端。

## 4. 去重：先用哈希分桶，比上复杂树更合适

`discovery_sessions.py:264` 的重叠去重，对每个新片段扫描全部已保留片段，只在文件和页码相同时才计算区间重叠。最坏比较数为 K(K−1)/2，当前 K≤400，因此单次上限约 79,800 对。

临时原型保留原输入次序、文字精确去重及 80% 重叠规则，只先按 `(asset_id, page)` 分桶。100 组固定种子随机样本与 6 组规模样本结果一致；这不是完整生产回归证明。

| 400 条样本 | 当前函数，3次中位数 | 哈希分桶原型，3次中位数 |
| --- | --- | --- |
| 同文件、不同页 | 33.3 ms | 2.3 ms |
| 同文件、同页且区间不重叠 | 68.2 ms | 32.0 ms |

分桶后复杂度为 O(K + Σkᵢ²)，多页分散时受益明显，同页集中时仍可能平方增长。区间树可减少无关区间比较，但需要严格保留按排名贪心去重的语义；按坐标排序后直接去重可能改变结果。当前 400 上限下，先采用小分桶原型验证即可，不优先引入区间树依赖。

## 5. OCR：检查点正确，剩余集合维护可以改进

`processing.py:889` 的普通分支读取该文件全部页面 `(index, text_source)`；`run_ocr_job()` 在单页处理前后各调用一次。P 页完成过程会产生约 2P² 条页面行读取。`all_pages` 分支不逐次查询页面，但每次也重建 completed 集合和 1..P 剩余列表，存在类似的累计 CPU 工作。

直接反复调用普通分支辅助函数，夹具页状态保持 native，不运行 OCR，用来隔离元数据扫描：

| P | 调用次数 | SQL 次数 | 返回页面行总数 | 本地耗时 |
| --- | --- | --- | --- | --- |
| 100 | 200 | 200 | 20,000 | 168 ms |
| 300 | 600 | 600 | 180,000 | 679 ms |
| 600 | 1,200 | 1,200 | 720,000 | 2,124 ms |

这个开销已经复现，但不能解释历史上“单页数分钟”的 OCR 延迟。真实瓶颈仍需拆测 PDF 打开/选页、压缩传输、排队、模型推理和保存。本地存储路径也不应被误说为每页重新传输整本 PDF：`ocr_provider.py` 对指定页提取子 PDF 后发送。

候选方案为记录当前任务的有序目标、已完成检查点和下一待处理页，在成功事务中推进计数；重试/恢复时从既有检查点重新校验。目标不连续、暂停、源文件变化、旧 worker 回写均须保持正确。保留每页落库，不用扩大失败损失窗口换取表面速度。

## 6. 树：减少数据库往返，先于改变树的存储方式

`editorial_revision.py:895` 只预取 parent 的下一层，然后 `while current is not None` 逐层访问 parent。环检测本身 O(h) 合理，但 ORM 往返也近似 O(h)。

| 人工合成深度 | 当前 SQL 数 | 一次读取同学科邻接表后遍历 |
| --- | --- | --- |
| 1 | 2 | 1 |
| 10 | 10 | 1 |
| 50 | 50 | 1 |
| 100 | 100 | 1 |

邻接表实验只比较祖先环检查，不是包含所有字段、权限和同学科校验的完整保存替代服务。它要付出 O(V) 的同学科读取及内存，对大而浅的树可能更差。真实层级分布尚未测量。

选择顺序：浅树低频编辑保留当前方案；节点量不大而要批量检查时用邻接表加 visited 集合；很大且只沿一条祖先链查询时比较 PostgreSQL 递归 CTE。闭包表需要新增维护和迁移，嵌套集合移动子树成本高，当前没有采用依据。并查集适合无向连通性，不能直接替代这里的有向父链环检查。[PostgreSQL 16 递归查询文档](https://www.postgresql.org/docs/16/queries-with.html)提供了原生路径及环检测能力。

## 7. 推理服务：需要实测的内存与延迟取舍

`inference_service/app.py:104` 的锁包住 normalize、chunk、embed、rerank；获取锁等待 3 秒后返回 429。`runtime.py:152/243` 在角色变化时释放当前 tokenizer/model，再加载另一个。搜索执行 embedding 后 rerank，下一次 embedding 又要换回；索引也使用 embedding。

因此“查询和索引各有一个 worker”不等于模型能并行执行，增加 Celery worker 也未必提高吞吐。源码已经证实共享和换载行为，但本轮没有模型加载耗时、429 频率、RSS 或排队分位数，不能把它定为当前线上主要瓶颈。

可比较：继续单模型常驻并给前台请求优先级；有内存证据后双模型常驻；使用另一个已授权执行节点。先测混合查询/索引下的队列等待、换载次数、p50/p95 和峰值内存。不要直接扩大模型、删除互斥或同时加载所有模型。
