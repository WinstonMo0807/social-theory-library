- 推理服务按需冷启动超过原客户端 15 秒窗口，首个请求可能在服务监听前失败。

## 修改

1. 元数据更新依据捕获的 DocumentRevision 质量评估继续请求全文投递，不再把上次投递失败视为正文不合格。只有真实投递完成才允许 fulltext_ready。
2. Discovery 对同一已接收 Meilisearch task 有界等待 300 秒，状态读取超时/HTTP 408 在原截止时间内继续轮询；显式失败仍失败。对应任务软/硬上限为 840/900 秒，涵盖检查点切片、冷启动、推理和索引等待。
3. 推理按需启动等待上限调整至 90 秒，其余按需服务仍为 15 秒。
4. 推理分块在句子边界选择后再次验证实际 token 数，必要时回到已经验证预算的原文切片，不丢弃文字、不放宽校验。
5. API、普通 worker、重任务 worker、查询 worker 同步上述代码及既有 ingestion/indexing、projection_refresh 修复。推理服务更新 runtime.py；模型文件和模型身份保持。
6. Discovery 协调器复用既有 broker_presence，同时检查 Redis 排队和保留的投递；超过一小时仍有消息的 pending 任务不误计中断，队列状态未知时延后判断。真实丢失投递和超时 running 任务保留原恢复路径。

未变更数据库结构、原始 PDF、人工正文、权限规则或活动索引身份。旧版本和成功片段保留。
