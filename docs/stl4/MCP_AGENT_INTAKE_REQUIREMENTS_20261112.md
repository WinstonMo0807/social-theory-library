# 智能体上传与馆藏更新的MCP接入要求

日期：2026-11-12。用户补充：上传者及馆藏维护者可能是智能体，不能假设管理员先手工入库，再交给MCP策展。

状态：D为已部署的动态馆藏草稿授权；C为本文件确定的入库扩展需求，尚未新增或部署上传MCP工具。本轮只审计源码和记录接口边界，没有上传、替换文件或修改生产数据。

## 已实现与尚缺的部分

`work_scope=catalog`覆盖现有及未来入库的Work，上传由人或智能体完成都适用。七个现有MCP工具可以读取这些作品、规范实体查重、取证、修改编目及知识对象草稿、保存并续做。它们尚不负责把本机PDF传到服务器，也不能仅凭一个新文件直接创建初始入库记录。

后端已有可复用的链路：

- [上传工作区](../../api/ingestion/upload_workspace.py)：按账户绑定的批次预留、固定request_id、请求指纹、版本检查和回执；同请求恢复，不重复创建批次。
- [上传接口](../../api/ingestion/views.py)：`BatchItemChunkUploadView`提供持久分片查询/接收、client_token去重、合并校验，另有既存R2上传会话；两者由上传工作区返回实际可用传输方式。
- [版本与文件服务](../../api/catalog/services/edition_file_intake.py)：supplement/replace、原版本及阅读文件凭据、暂存和后续处理；不得把旧兼容替换入口当成绕过新工作区校验的方法。
- [批次策略](../../api/ingestion/serializers.py)：文件数、访问范围、OCR及查重策略。当前上传工作区每批至多50份，智能体按批次拆分，不以此限制馆藏总量。

## 用户流程与更新语义

| 智能体任务 | 应走的流程 |
| --- | --- |
| 上传一本新书 | 建立/恢复上传批次→传输→校验/查重→原入库处理→取得Work/Edition→立即使用动态授权策展 |
| 补充译本或另一出版版本 | 明确所属Work和新Edition，不因书名相同直接合并版本；文件走原入库/版本流程 |
| 为书目补首份PDF | 指定已有Edition，复用supplement及版本凭据；保留已有编目和知识关系 |
| 上传更清晰的扫描或修正文件 | 指定目标Edition和当前阅读文件版本，复用暂存、影响预览及采用流程；原件、历史、笔记和证据定位保留 |
| 更新书名、人物、主题或理论关系 | 继续使用prepare/save草稿及现有发布流程，不靠重新上传PDF改写这些字段 |

用户已授权的批次可连续运行，不给每份正常文件另加确认步骤。重复文件、作品/版本归属歧义、旧版本凭据或人工锁冲突返回具体问题，保留已成功项及原计划，不盲目新建另一份馆藏。

## 下一步工具与文件通道

拟增加`stl_prepare_uploads`和`stl_get_ingestion_status`两个面向任务的工具，名称为设计，不是当前已存在的工具。前者建立/恢复上传计划，记录新增/补充/替换意图、文件名/大小/哈希、目标Work/Edition、已有版本及固定请求编号；后者查实际分片、UploadItem、原处理任务和回执，并返回可继续策展的实体ID。

PDF字节由本机/客户端上传辅助程序通过现有分片或对象存储会话传输。MCP只传元数据、计划、状态和回执，不把大PDF编码进模型工具参数，不要求网关加载整书或提高现有MCP控制请求上限。辅助程序从服务端读取实际分片大小、文件上限和已接收片段；中断后复用原batch/client_token，仅补缺失部分。

文件提交的完成点沿已有传输协议，不再增加平行的文件存储、上传数据库或OCR管道。接收、校验、正文处理、索引、草稿和公开状态分别返回；收到文件不能报成已完成策展或正式发布。OCR/索引仍走原任务系统及资源限制，不在MCP进程运行，也不因一次上传重跑整个馆藏。

## 授权和数据保护

上传要使用原`CanUpload`/`Capability.UPLOAD`，继续绑定本人账户、批次归属和当前token_version。现在的MCP Bearer只认证MCP，不能把它直接当作REST API登录令牌；接入上传辅助程序时必须实现受限的传输授权。若采用短期上传票据，票据仅限指定账户、批次、文件大小/哈希和目标操作，不向客户端发放馆长通用API令牌，不提供任意URL代理或服务器文件路径读取。

只上传文件不自动取得切换公开正文、删除旧资产、合并作品/人物、解除锁或正式发布的权限。用户明确授权的文件更新仍按原工作区影响检查和版本校验执行；元数据和知识内容沿现有草稿/发布流程。普通新入库文献自动进入catalog范围，不需要再申请作品UUID。

## 实施时的必要验证

验证真实链路中的新文件入库、同文件重试/断点续传不重复、同Work不同Edition、补首份PDF、修正文件暂存与历史保留、旧版本冲突和他人批次拒绝。隔离测试后才用用户指定的真实文件演示；上传是否完成、后台处理和公开状态分别留回执。当前没有运行这些新增MCP上传工具的验证，不能据已有REST代码或已通过的43项策展检查声称上传MCP已经接通。
